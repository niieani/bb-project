## Release signing

The current Homebrew cask flow downloads quarantined Darwin archives directly from GitHub Releases. That means Gatekeeper evaluates the `bb` executable exactly as published. Until now the release pipeline produced unsigned, unnotarized macOS binaries, which made the cask install path fail at first launch even though the release itself was otherwise healthy.

The leverage point is the release pipeline, not the cask. Homebrew is doing the correct thing by preserving quarantine. The fix is to make the published Darwin artifacts satisfy Apple's outside-the-App-Store distribution requirements: Developer ID signing with a secure timestamp and notarization through App Store Connect credentials. Because `bb` ships standalone binaries rather than app bundles, GoReleaser's cross-platform macOS notarization path is the right fit and avoids introducing a macOS-specific keychain setup into CI.

The release system already centralizes asset publication in GoReleaser, so the right strategy is to teach the existing GoReleaser config how to sign and notarize the Darwin build artifacts and to pass the required secrets into every workflow entry point that can publish a release. The initial pass used direct GitHub secrets for all Apple materials, but the better operational model is to keep the long-lived materials in 1Password and use the GitHub workflow only for the 1Password service-account token. The next cleanup is architectural rather than security-focused: move the duplicated publish job behind a reusable workflow so the mainline `release-please` path and the manual tag-republish path both call the same implementation.
